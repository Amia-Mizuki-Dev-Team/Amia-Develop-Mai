# 08 · 加密版本代际

本文描述业务 API 通道加密参数随客户端版本迭代的演进：两代参数组的结构差异与版本探测机制。

## 一、代际总览

业务通道的加密参数组随机台 ROM 版本迭代更新。已观察到两个代际：

| 代际 | 请求头 Mai-Encoding | ROM 版本上报 | 对应客户端版本 |
|---|---|---|---|
| 旧代（1.53 组） | `1.53` | 1.53 / 1053000 | 1.53 系列机台 |
| 新代（1.55/1.56 组） | `1.55` | 1.55 / 155 | 1.55 与 1.56 系列机台 |

- **算法完全一致**（JSON → zlib → PKCS7 → AES-256-CBC，见 02）
- 差异仅在三个参数：AES 密钥、AES 初始向量、端点混淆参数
- 新代中 1.55 与 1.56 两个命名版本使用**同一组**参数（仅命名与阈值判定不同）

## 二、参数组结构

每代参数组包含四项（**值一律不公开**）：

| 参数 | 结构特征 | 用途 |
|---|---|---|
| key | 32 字节字符串 | AES-256-CBC 密钥 |
| iv | 16 字节字符串 | AES-CBC 初始向量 |
| encoding | `1.53` / `1.55` | 请求头 Mai-Encoding |
| obfuscate | 8 字符短字符串 | 端点哈希混淆参数（见 02） |

两代的结构差异示意（真实值以 `<已脱敏>` 占位）：

```
旧代(1.53组):  { key: <已脱敏>, iv: <已脱敏>, encoding: "1.53", obfuscate: <已脱敏> }
新代(1.55组):  { key: <已脱敏>, iv: <已脱敏>, encoding: "1.55", obfuscate: <已脱敏> }
新代(1.56组):  { key: <同上>,    iv: <同上>,    encoding: "1.55", obfuscate: <同上> }
```

## 三、跨代共用的参数

二维码鉴权通道的**鉴权盐**（AUTH_SALT，见 03）在两代之间保持不变——即新旧机台的二维码鉴权签名使用同一盐值（值不公开）。

## 四、ROM 版本上报

机台初始化时通过 `UpsertClientSettingApi` 的 `romVersion` 字段上报 ROM 版本：

- 数值形式：主版本号 × 100 + 次版本号（如 1.55 → 155）
- 旧代实现亦有四位数值形式（如 1053000 对应 1.53）
- 服务器依据该字段维护玩家"最后使用的客户端版本"（lastRomVersion）

## 五、版本探测机制

玩家可能在不同代际的机台上游玩，因此协议实现需在会话开始前探测该玩家应使用的参数组：

```
1. 尝试以新代参数组调用玩家预览接口
2. 读取响应中的 lastRomVersion 字段
3. 判定:
     lastRomVersion ≥ 1.56.00 → 使用新代(1.56)参数组，预览结果直接复用
     lastRomVersion <  1.56.00 → 使用新代(1.55)参数组，需重新预览
     新代预览失败/不可用      → 降级到旧代参数组
```

该机制的观察依据是"玩家数据中记录的客户端版本"与"服务端接受的加密参数"存在对应关系。

## 六、参数轮换的含义

- 加密参数随版本轮换，属于官方对协议通道的常规演进
- 旧代参数组在旧机台退役前仍需兼容支持，因此协议实现普遍同时内置两代配置
- 抓包比对可验证：同一接口在新旧代的请求头 `Mai-Encoding` 与端点哈希不同，但语义完全一致
