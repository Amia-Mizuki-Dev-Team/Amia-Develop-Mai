# 08 · 加密版本代际

本文描述业务 API 通道加密参数随客户端版本迭代的演进：参数组结构与版本探测机制。

## 一、代际总览

业务通道的加密参数组随机台 ROM 版本迭代更新。**当前线上仅一个现役代际**：

| 代际 | 请求头 Mai-Encoding | ROM 版本上报 | 对应客户端版本 |
|---|---|---|---|
| 现役（1.55 组） | `1.55` | 1.55 / 155 | 1.55 系列机台 |

- 更早的历史代际（1.53 组）随旧机台/旧服务端退役已不再可达，现役实现无需兼容
- **算法在各代际间完全一致**（JSON → zlib → PKCS7 → AES-256-CBC，见 02）
- 代际之间的差异仅在三个参数：AES 密钥、AES 初始向量、端点混淆参数

## 二、参数组结构

每个参数组包含四项（**值一律不公开**）：

| 参数 | 结构特征 | 用途 |
|---|---|---|
| key | 32 字节字符串 | AES-256-CBC 密钥 |
| iv | 16 字节字符串 | AES-CBC 初始向量 |
| encoding | `1.55` | 请求头 Mai-Encoding |
| obfuscate | 8 字符短字符串 | 端点哈希混淆参数（见 02） |

参数组结构示意（真实值以 `<已脱敏>` 占位）：

```
现役(1.55组):  { key: <已脱敏>, iv: <已脱敏>, encoding: "1.55", obfuscate: <已脱敏> }
```

## 三、跨代共用的参数

二维码鉴权通道的**鉴权盐**（AUTH_SALT，见 03）在各代际之间保持不变——即不同代际机台的二维码鉴权签名使用同一盐值（值不公开）。

## 四、ROM 版本上报

机台初始化时通过机台设置上报接口的版本字段上报 ROM 版本：

- 常用数值形式：主版本号 × 100 + 次版本号（如 1.55 → 155）
- 游玩记录（playlog）中亦使用数值化版本戳（如 1.55 → 1055000，即 主×1000000 + 次×1000）
- 服务器依据该字段维护玩家最后使用的客户端版本信息

## 五、版本探测机制（为 1.60 预留）

参数轮换会随版本演进再次发生（下一个预期代际为 1.60）。成熟的协议实现普遍保留
**版本过滤骨架**：会话开始前探测该玩家应使用的参数组，探测失败自动回退现役组。

```
1. 尝试以最新参数组调用玩家预览接口
2. 读取响应中的客户端版本字段
3. 判定:
     客户端版本 ≥ 切换阈值 → 使用新参数组，预览结果直接复用
     客户端版本 <  切换阈值 → 回退现役参数组，需重新预览
     探测失败/新组未注册   → 回退现役参数组
```

当前线上仅 1.55 一代，探测即直通现役组；新参数组注册进配置后，上述两级判定
自动生效，无需改动调用方。

该机制的观察依据是"玩家数据中记录的客户端版本"与"服务端接受的加密参数"存在对应关系。

## 六、参数轮换的含义

- 加密参数随版本轮换，属于官方对协议通道的常规演进
- 单代现役期内实现只需内置一组配置；新代际上线时通过注册新参数组 + 版本过滤
  平滑过渡，历史代际随旧服务端退役自然淘汰
- 抓包比对可验证：不同代际的请求头 `Mai-Encoding` 与端点哈希不同，但语义完全一致
