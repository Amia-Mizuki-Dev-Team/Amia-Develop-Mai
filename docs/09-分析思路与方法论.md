# 09 · 分析思路与方法论

本文面向**公共开发者**，讲述"这类街机协议是如何被分析出来的"——全部为思路与方法层面，不涉及任何接口名称、凭据与构造细节。

## 一、总思路：把未知协议拆成五个问题

分析任何一个私有协议，本质上是回答五个问题，并让答案相互印证：

1. **数据怎么封装**（传输层：压缩、加密、编码）
2. **端点怎么寻址**（URL 语义、路由规则）
3. **身份怎么证明**（鉴权、签名、会话）
4. **流程怎么走**（会话时序、状态机）
5. **数据从哪来**（静态数据与动态数据的分工）

本文按这五个问题组织。

## 二、观察起点：流量特征

一切分析的起点是**合法流量的观察**（本文不讨论流量的获取方式）。拿到流量样本后，先记录三类宏观特征：

- **长度规律**：密文长度随业务变化是否连续（提示压缩参与）、是否对齐到固定分块（提示分组加密）
- **熵特征**：密文的高熵与明文 JSON/XML 的低熵有显著差异，可作为"哪里开始是密文"的切分依据
- **固定头尾**：URL 的固定路径段、固定请求头字段，往往暴露技术栈与通道身份

## 三、封装识别：从"看不懂"到"看得懂"

密文 → 明文的还原链通常由若干"可逆变换"叠加而成，识别思路是逐层剥离：

- **压缩先于加密**：若解密后仍是高熵数据但长度明显缩短，优先怀疑压缩（zlib 有固定头特征）
- **填充特征**：分组加密的填充块使密文长度对齐分块大小
- **编码习惯**：结构化数据的序列化风格（紧凑/带空白）在解密后会直接暴露

常见组合是"序列化 → 压缩 → 分组加密"，本仓库 02 文档即该组合的一个实例。

## 四、端点语义反推：哈希路由的破解思路

当 URL 路径是哈希值时，语义不可读，但可反推：

- **猜想-比对**：准备一组候选名称（从功能、命名习惯猜测），逐一计算哈希并与抓包值比对；命中即锁定语义
- **固定后缀参与哈希**：哈希输入往往带平台标识后缀，反推时需要将后缀纳入计算
- **用流量对应关系交叉验证**：同一次会话中不同路径的出现顺序与已知业务流程比对，确认命名归属

## 五、身份与鉴权：从请求里读协议

- **签名素材**：观察鉴权请求中的关键字段（设备标识、时间戳、校验值），通过"拼接-哈希-比对"验证签名算法
- **时间戳语义**：鉴权值随时间变化且可复现，说明时间戳参与签名；对比多组样本可锁定时间格式
- **会话凭证流转**：追踪凭证在后续请求中的携带位置（头字段/请求体），确定会话边界

## 六、版本代际跟踪：参数轮换的观察方法

加密参数随客户端版本迭代轮换，跟踪思路：

- **新旧流量对比**：同一接口在新旧版本的抓包样本做字段级 diff，差异即轮换参数的作用位置
- **版本字段定位**：找出请求中上报版本号的字段，以它关联参数组
- **兼容窗口**：旧参数组在新版本退役前通常仍然有效，可据此构建多代兼容的探测逻辑（思路见 05）

## 七、静态数据与动态数据的分工

完整图景由两类数据拼成：

| 类型 | 来源 | 内容 |
|---|---|---|
| 静态数据 | 更新分发通道的产物（资源包） | 乐曲、谱面、定数、活动定义等 |
| 动态数据 | 业务通道的会话接口 | 玩家状态、成绩、库存等 |

分析顺序建议：**先静态后动态**——静态数据提供字典（ID 与名称的映射、谱面信息），动态数据解析时用它做语义还原。

## 八、验证闭环：假设驱动的迭代

协议分析是"假设-验证"循环，而非一步到位：

```
观察样本 → 提出假设（如"先 zlib 后 AES"）
  → 构造最小验证（用最小可用数据做一次变换）
  → 比对结果（与抓包样本一致？）
  → 修正假设 → 重复
```

原则：

- **最小验证优先**：用一条最短的样本验证每一步变换，避免组合错误难以定位
- **一条链路走通再扩展**：先还原"一个请求"的完整封装，再横向推广到全部接口
- **保留反例**：无法解释的样本往往指向被忽略的分支逻辑（兼容模式、异常路径）

## 九、分析者的合规红线

- 分析只记录**原理与思路**，不公开可复现的凭据（密钥、盐、服务器地址）
- 不提供成品工具或可直接运行的客户端
- 文档定位为技术研究，禁止任何破坏服务、作弊、盗取数据或商业用途
