# 05 · 会话生命周期

本文描述一次完整的业务会话：从机台上电初始化到玩家登出，各阶段调用的接口与时序。

## 一、完整时序总览

```
机台初始化(机台级请求)
  Ping → UpsertClientSetting → UpsertClientTestmode → GetGame*系列(游戏内容)
      ↓
玩家入场
  二维码鉴权(鉴权库) → 获得 userID + token
      ↓
登录前预检
  GetUserPreview → 检查 isLogin / 探测加密代际
      ↓
建立会话
  UserLogin → returnCode=1 → loginId
      ↓
数据拉取
  基础数据(单次类) → 内容数据(分页类)
      ↓
数据写入(可选)
  UpsertUserAll / UploadUserPlaylogList / UpsertUserChargelog
      ↓
续关(批量场景，可选)
  UserLogin(isContinue=true) → 继续拉取/写入
      ↓
登出
  UserLogout(type=1/4/5, delayLog) → returnCode=1
```

## 二、机台初始化阶段

机台级请求的身份段为 keychip ID（而非 userId），顺序如下：

| 步骤 | 接口 | 关键内容 |
|---|---|---|
| 1 | Ping | 连通性探测 |
| 2 | UpsertClientSettingApi | 门店、区域、ROM 版本、isAou（是否 AOU 机台） |
| 3 | UpsertClientTestmodeApi | 轨道配置（单机/多机）、卫星、摄像头位 |
| 4~11 | GetGame* 系列 | 活动、票务、排行、禁曲、屏蔽词、万花筒、周常、锦标赛 |

初始化阶段的产物包括**禁用乐曲列表**与**屏蔽词表**，供后续过滤使用。

## 三、登录前预检

`GetUserPreviewApi` 在正式登录前调用，作用有二：

1. **占用检查**：`isLogin == true` 表示玩家已在其他机台登录，必须先登出才能继续
2. **版本探测**：读取 `lastRomVersion` 判断玩家使用的客户端代际，选择加密参数组（见 08）

响应还包含 `userName`、`playerRating`、`banState`（封禁状态）等概要信息。

## 四、建立会话（UserLoginApi）

请求体关键字段：

| 字段 | 取值 | 说明 |
|---|---|---|
| userId | 鉴权所得 | 玩家 ID |
| accessCode | 空字符串 | 固定 |
| regionId / placeId / clientId | 机台凭据 | 区域/门店/机台芯片 |
| dateTime | 当前时间减 600 秒 | 会话起始偏移 |
| loginDateTime | 当前时间 | 登录时刻，登出时需原样回传 |
| isContinue | false / true | 首次登录为 false，续关为 true |
| genericFlag | 0 | 固定 |
| token | 鉴权所得 | 会话凭证 |

成功判定：`returnCode == 1`，响应含 `loginId` 与 `lastLoginDate`。

**续关（isContinue = true）**：批量上传场景中，一次会话完成一批写入后，再次以 `isContinue=true` 调用登录接口开启"续关"，避免长时间占用单一会话。

## 五、数据拉取

### 单次类接口

一次请求即返回完整数据：基础档案、扩展、设置、Rating、活动、任务、区域、角色等（见 04 第五组）。

### 分页类接口

以"游标 + 每页条数"分页，规则统一：

```
请求: { userId, nextIndex: 游标, maxCount: 每页条数 }
响应: { ...列表, nextIndex: 下一页游标 }
终止条件: 响应 nextIndex == 0
```

- **GetUserMusicApi**：`maxCount = 100`，聚合结构 `userMusicList[].userMusicDetailList[]`（一首歌多个难度）
- **GetUserItemApi**：按物品类目分段，**初始游标 = 类目编号 × 10^10**，依次遍历类目序列（如 [1,2,3,10,11,12,14,4,5,6,7,8] 或按实现调整），类目内再翻页至 `nextIndex == 0`

## 六、数据写入

| 场景 | 接口 | 说明 |
|---|---|---|
| 全量同步 | UpsertUserAllApi | 上行 20+ 段全量数据 + 游玩记录（结构见 06） |
| 游玩记录 | UploadUserPlaylogListApi | 单曲/批量游玩记录 |
| 票务 | UpsertUserChargelogApi | 购票流水与库存（见 06） |

写入类请求与登出之间通常保持约 60 秒间隔（协议实现观察值，疑似服务端侧的会话节流窗口）。

## 七、登出（UserLogoutApi）

请求体关键字段：

| 字段 | 说明 |
|---|---|
| userId, accessCode, regionId, placeId, clientId | 与登录一致 |
| loginDateTime | 登录时刻（原样回传） |
| type | 1 = 正常登出；4 = 异常登出；5 = 其他（各实现取值略有差异） |
| delayLog | 性能统计（仅正常登出携带，见下） |

成功判定：`returnCode == 1`，或短确认响应/空响应（见 02）。

### delayLog 性能统计结构

游戏客户端在登出时向服务端上报本次会话的接口性能统计：

```
delayLog = {
  dlRequests: 总请求次数,
  dlSize:     总字节数,
  dlRetry:    总重试次数,
  loginMsec:  登录耗时(毫秒),
  saveMsec:   存档耗时(毫秒),
  reductionMusic: 乐曲数据缩减量,
  reductionItem:  物品数据缩减量,
  request: [ {count, size, msec, retry} × 26 ]   # 按接口索引统计，取前 26 项
}
```

### 三次登出策略

协议实现普遍采用"三次登出"增强可靠性：连续调用登出接口最多 3 次、每次间隔 2 秒、任一次成功即视为登出成功。原因：服务端偶发返回非成功或连接异常，多试几次可显著降低"假登录占用"（玩家被卡在已登录状态）的概率。

## 八、异常路径

- 预检发现 `isLogin == true` → 拒绝登录，提示先登出
- 登录后流程异常 → 以 `type=4`（异常登出）结束会话释放占用
- 登出失败 → 进入重试（三次登出），仍失败则等待超时后由调度器兜底
