# 09 · 更新分发通道

本文描述与业务 API 完全独立的**更新分发通道**（ALL.Net delivery）：机台如何获得更新指示书、如何下载与解密更新包。

## 一、通道定位

| 对比项 | 业务 API 通道 | 更新分发通道 |
|---|---|---|
| 用途 | 玩家数据读写 | 游戏客户端更新包下发 |
| 加密 | AES-256-CBC + zlib + 端点哈希 | LITE 认证（AES-CBC + 随机前缀） |
| 载体 | JSON | key=value 文本、INI、二进制包 |
| 身份 | keychip + 玩家 token | 设备序列号（client_id） |

更新分发通道的产物（解密后的更新包）是**游戏静态数据**的唯一来源：乐曲、角色、万花筒之门、地图、活动等 XML，下游协议实现的曲库与定数数据均由此而来。

## 二、LITE 认证加密

机台以"Lite 客户端"身份向指示书服务器请求更新信息，请求体为一小段 `key=value` 文本，经 AES-CBC 加密：

### 请求加密

```
明文   = "title_id=<游戏ID>&title_ver=<版本>&client_id=<设备序列号>"
            # 游戏ID/版本/序列号均为固定标识（值不公开）
填充前 = 32字节随机前缀 + 明文
密文   = AES_CBC( PKCS7填充(填充前), key=固定16字节密钥, iv=全零16字节 )
请求体 = 密文（直接作为 HTTP 正文）
```

- 密钥为固定 16 字节数组（值不公开），初始向量为全零
- 32 字节随机前缀使同一明文每次加密结果不同

### 响应解密

```
响应体格式(新版): [16字节随机IV][AES密文]
响应体格式(旧版): [AES密文]（无 IV 前缀，兼容处理）
解密后: 过滤不可打印字符 → key=value 文本
```

### 请求头特征

- `User-Agent` 形如 `<游戏ID>;Windows/Lite`（游戏 ID 值不公开）
- `Pragma: DFI` 等固定字段

### 设备序列号（client_id）

序列号以**密文**形态存储在客户端配置中，运行时经带盐的对称解密还原（解密盐与密文值均不公开）。这一设计使序列号不直接以明文落盘。

## 三、指示书与更新配置

指示书响应为 `key=value` 文本：

```
result = 1                 # 1 表示成功
uri    = URL1|URL2|...     # 以竖线分隔的多个更新指示书地址
```

逐个请求指示书地址，得到 **INI 格式**的更新配置：

| 段 | 键 | 含义 |
|---|---|---|
| COMMON | INSTALL1 | 主更新包下载地址 |
| COMMON | PART_SIZE | 机台接收限速（逗号分隔） |
| COMMON | GAME_ID | 游戏标识 |
| COMMON | GAME_DESC | 更新描述 |
| COMMON | ORDER_TIME | 允许开始下载的时间 |
| COMMON | RELEASE_TIME | 实际应用更新的时间 |
| OPTIONAL | install* | 历史可选更新包 |

更新包按描述前缀分类：`OPTION` 前缀为**数据包**（Opt），`PATCH` 前缀为**程序包**（App）。下载时间窗：`ORDER_TIME` 前 24 小时即可预下载。

## 四、更新包下载机制

| 机制 | 说明 |
|---|---|
| 大小探测 | 先发 HEAD 请求取 Content-Length；失败则回退 `GET + Range: bytes=0-0`，从 Content-Range/Content-Length 推断总大小 |
| 断点续传 | `.part` 临时文件 + `Range` 请求，中断后从断点继续 |
| 分块多线程 | 每块约 1 MiB，先开 3 线程后追加 2 线程 |
| 限速 | 单线程约 10 MB/s，多线程约 5 MB/s |
| 错误 567 | CDN 节点超时，连续 3 次即终止本次下载 |
| 错误 416 | Range 不满足，重置下载 |

## 五、更新包解密（fsdecrypt）

下载的 `.opt` / `.vhd` 为加密产物，需经专用解密工具（外部二进制，按平台/架构分发）解密：

```
.opt 更新包 → 解密 → 数据目录（按版本号命名）
.app 程序包 → 解密 → .vhd 虚拟磁盘 → 再解密 → 游戏文件
```

解密产物即游戏静态数据，典型目录结构：

```
music/            # 乐曲与谱面
chara/            # 角色
kaleidxScope/     # 万花筒之门/钥匙/条件/音乐组
title/            # 称号
map/              # 地图
event/            # 活动
```

这些 XML/资源文件是下游曲库、定数表、谱面数据的源头（数据流关系见 01-协议体系总览）。

## 六、通道要点小结

- 更新分发通道与业务通道**无交集**：独立的服务器、独立的加密、独立的身份体系
- 三处凭据均不公开：LITE 认证密钥、序列号密文与解密盐、服务器地址
- 该通道的逆向价值在于"稳定获取最新游戏静态数据"，是下游一切数据解析的基础设施
