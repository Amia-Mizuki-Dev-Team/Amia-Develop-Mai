# 02 · 传输与加密

本文描述业务 API 通道（Maimai2Servlet）的传输层：请求体如何封装、端点如何寻址、请求头如何构造。

## 一、请求体加密流水线

所有业务接口的请求体都经过固定的三步封装，响应体逆向解封：

```
请求方向:  结构化数据 → 紧凑JSON序列化 → zlib压缩 → PKCS7填充 → AES-256-CBC加密 → 密文字节流
响应方向:  密文字节流 → AES-256-CBC解密 → 去填充 → zlib解压(失败则按裸JSON) → 结构化数据
```

伪代码描述：

```
请求体 = AES_CBC_加密(
            PKCS7_填充(
                zlib_压缩(
                    紧凑JSON_序列化(请求数据)
                )
            ),
            key=密钥, iv=初始向量
        )
```

要点：

- **紧凑 JSON**：序列化时不带多余空白（分隔符取最小形式），保证压缩前体积稳定
- **zlib**：请求头 `Content-Encoding` 标注为 `deflate`，实际使用的是 zlib 封装格式
- **AES-256-CBC**：密钥 32 字节、初始向量 16 字节（各代际参数值均不公开，见 05）
- **PKCS7 填充**：按 AES 分块大小（16 字节）填充

## 二、端点混淆

业务接口的实际 URL 路径不直接使用接口名，而是经过哈希变换：

```
路径 = md5( 接口名 + 国服标识后缀 + 混淆参数 )
```

- `接口名`：业务接口的内部名称（属隐私，不公开）
- 国服标识后缀：固定后缀，参与哈希
- `混淆参数`：随加密代际变化的短字符串（值不公开）
- 结果：32 位十六进制字符串，作为 URL 的最后一段路径
- 完整 URL 形如：`<已脱敏的服务器基址>/<业务Servlet路径>/<32位哈希>`（服务器地址与路径段均不公开）

这一机制使抓包时无法从 URL 直接得知接口语义，需结合哈希反查才能定位。

## 三、请求头

| 头字段 | 值 | 说明 |
|---|---|---|
| `Content-Type` | `application/json` | 固定 |
| `Content-Encoding` | `deflate` | 标注为 deflate，实际为 zlib |
| `Mai-Encoding` | `1.53` 或 `1.55` | 标识加密代际（见 08） |
| `Accept-Encoding` | 空 | 要求不压缩传输 |
| `Charset` | `UTF-8` | 固定 |
| `Host` | 服务器主机 | 由基址解析 |
| `User-Agent` | `<哈希>#<身份>` | 见下文 |

### User-Agent 的构造

```
User-Agent = 端点哈希 + "#" + 身份标识
```

- 机台级请求（未登录玩家）：身份标识为机台 `keychip` ID
- 玩家级请求：身份标识为玩家 `userId`

## 四、响应处理细节

### 短响应

解密后的明文长度小于 32 字节时，先尝试直接按 UTF-8 解码：

- 长度不超过 16 字节的短文本视为"短确认信号"，按成功处理
- 典型场景：登出接口返回极短的确认内容

### 解压回退

zlib 解压失败时，回退为对解密明文直接做 JSON 解析（兼容服务端未压缩的响应）。

### 空响应

接口返回空正文时，登出类接口按成功处理（`returnCode = 1`），其余接口视为失败。

## 五、TLS 行为说明

逆向研究工具链中的客户端普遍**忽略证书校验**（便于抓包分析）；官方客户端行为与之不同。本文档仅记录协议事实，不建议在任何正式环境中模仿该做法。

## 六、加密参数的结构（值不公开）

每代加密配置包含三个参数，结构如下：

| 参数 | 类型 | 用途 |
|---|---|---|
| AES 密钥 | 32 字节字符串 | AES-256-CBC 加密密钥 |
| AES 初始向量 | 16 字节字符串 | AES-CBC 初始向量 |
| 混淆参数 | 短字符串 | 端点哈希的附加盐 |

三者的真实取值均**不公开**（以 `<已脱敏>` 占位），代际差异见 08-加密版本代际。
